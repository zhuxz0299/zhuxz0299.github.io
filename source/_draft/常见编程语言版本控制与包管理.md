{% note primary %}
本文主要讨论两类问题：

1. **语言/运行时版本控制**：如何在同一台机器上安装、切换和固定不同版本的 Python、Node.js、JDK、.NET SDK、Rust 工具链或 C/C++ 编译器。
2. **包管理/依赖管理**：如何声明项目依赖、下载第三方库、生成锁文件，并尽量保证不同机器上的构建结果一致。
{% endnote %}

## 总览

不同语言生态对“版本控制”和“包管理”的边界划分并不完全一样：

| 语言 | 版本控制常用工具 | 包/依赖管理常用工具 | 典型配置文件 | 锁文件 |
|------|------------------|---------------------|--------------|--------|
| Python | uv、conda、pyenv | uv、pip、venv、Poetry、PDM、conda | `pyproject.toml`、`.python-version`、`requirements.txt`、`environment.yml` | `uv.lock`、`poetry.lock`、`pdm.lock`、`conda-lock.yml` |
| Node.js | fnm、nvm、Volta、asdf | npm、pnpm、Yarn、Corepack | `package.json`、`.node-version`、`.nvmrc` | `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock` |
| C# / .NET | global.json、系统包管理器、dotnet-install、asdf | NuGet、dotnet CLI | `.csproj`、`.sln`/`.slnx`、`Directory.Packages.props`、`NuGet.config` | `packages.lock.json` |
| Java | SDKMAN!、archlinux-java、asdf、jEnv | Maven、Gradle | `pom.xml`、`build.gradle(.kts)` | `gradle.lockfile`、Maven 需额外插件/策略 |
| Rust | rustup | Cargo | `Cargo.toml` | `Cargo.lock` |
| C/C++ | 系统包管理器、update-alternatives、CMake toolchain、vcpkg manifest | CMake、Meson、Conan、vcpkg、系统包管理器 | `CMakeLists.txt`、`meson.build`、`conanfile.*`、`vcpkg.json` | `conan.lock`、`vcpkg-configuration.json`/baseline、少量工具有自己的 lock |

{% note info %}
这里的“版本控制”不是 Git 那种源代码版本控制，而是指**语言版本/运行时版本/编译器版本的管理**。
{% endnote %}

## Python

Python 生态里最容易混淆的地方是：**Python 解释器版本**、**虚拟环境**、**第三方包依赖**经常由不同工具负责。过去常见组合是 `pyenv + venv + pip`，现在如果从新项目开始，可以优先把主线放在 `uv` 上。

### uv

`uv` 的定位不是单纯替代 `pip`，而是想把 Python 项目的几个常见动作统一起来：

- 管理 Python 版本
- 创建和维护项目虚拟环境
- 管理 `pyproject.toml` 里的依赖
- 生成 `uv.lock`
- 运行脚本和命令行工具

常用命令：

```bash
uv init demo
cd demo
uv python install 3.12
uv python pin 3.12
uv add requests
uv run python main.py
uv sync
```

`uv python pin 3.12` 会写入 `.python-version`，表示这个项目希望使用的 Python 版本。之后 `uv run`、`uv sync` 等命令会根据项目配置创建或更新 `.venv`，并根据 `pyproject.toml` 和 `uv.lock` 同步依赖。

一个最小的 `pyproject.toml` 可能长这样：

```toml
[project]
name = "demo"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.32",
]
```

`uv.lock` 记录解析后的完整依赖树，应用项目通常应该提交。`.venv/` 是本机虚拟环境目录，不应该提交。

```gitignore
.venv/
```

### uv 与传统工具的关系

`uv` 并不要求完全抛弃旧工具。它可以覆盖很多原来分散在不同工具里的职责：

| 传统工具/概念 | uv 中的大致对应 |
|---------------|-----------------|
| `pyenv` | `uv python install`、`uv python pin` |
| `python -m venv` | `uv sync` 自动创建 `.venv` |
| `pip install` | `uv add` 或 `uv pip install` |
| `pipx` | `uvx` / `uv tool run` / `uv tool install` |
| `requirements.txt` | `pyproject.toml + uv.lock`，也可以 `uv export` 导出 |

如果维护的是老项目，仍然会见到下面这种经典写法：

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install requests
python -m pip freeze > requirements.txt
python -m pip install -r requirements.txt
```

这种方式简单直接，但 `requirements.txt` 更像“已安装包列表”，不太擅长区分直接依赖和间接依赖。

### 其它常见选择

- `conda` / `mamba`：既能管理 Python 版本，也能管理依赖和虚拟环境，常用于数据科学、机器学习场景。它们可以处理不少 Python 之外的二进制依赖。
- `Poetry` / `PDM`：围绕 `pyproject.toml` 做项目依赖、虚拟环境、锁文件和打包发布。
- `pyenv`：专注管理多个 Python 解释器版本。现在新项目未必优先选它，但很多旧环境和教程仍然会出现。

使用 Poetry 的命令大致是：

```bash
poetry init
poetry add requests
poetry install
poetry run python main.py
```

### Python 小结

普通应用项目可以优先考虑：

- `uv` 管 Python 版本和项目环境
- `pyproject.toml` 声明依赖
- `uv.lock` 固定依赖版本
- `.venv/` 放在 `.gitignore`

如果是数据科学项目，`conda` / `mamba` 仍然很常见，因为它们可以处理一些 Python 之外的二进制依赖。

## Node.js

Node.js 生态的特点是工具很多，但主线比较清晰：

- **Node.js 运行时版本**：由 `fnm`、`nvm`、Volta 等工具控制。
- **包管理器版本**：`npm` 随 Node.js 自带；`pnpm`、`Yarn` 可以由 Corepack 或全局安装提供。
- **项目依赖版本**：由 `package.json` 和锁文件控制。

### Node.js 版本管理

常见选择：

- `fnm`：用 Rust 写的快速版本管理工具，支持 `.node-version` 和 `.nvmrc`。
- `nvm`：老牌 Node.js 版本管理工具，Linux/macOS 上非常常见。
- `Volta`：强调项目级工具链固定，可以固定 Node.js、npm、pnpm、Yarn 等版本。
- `asdf`：通用版本管理器，可以管理多种语言。

`fnm` 和 `nvm` 的核心命令非常像，例如安装、切换和设置默认版本：

```bash
fnm install 22
fnm use 22
fnm default 22

nvm install 22
nvm use 22
nvm alias default 22

node -v
```

项目中可以提交 `.node-version` 或兼容 `nvm` 的 `.nvmrc`：

```text
22
```

进入项目后执行：

```bash
fnm use
nvm use
```

如果 shell 配置了 `fnm env --use-on-cd`，`fnm` 还可以在进入目录时根据 `.node-version` 或 `.nvmrc` 自动切换。

### 包管理

Node.js 项目的核心文件是 `package.json`：

```json
{
  "name": "demo",
  "version": "0.1.0",
  "packageManager": "pnpm@11.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^6.0.0"
  }
}
```

常见包管理器：

- `npm`：Node.js 官方自带，所以安装某个 Node.js 版本后一般就有对应的 `npm`。
- `pnpm`：通过内容寻址存储减少磁盘占用，安装速度快，monorepo 支持较好。
- `Yarn`：曾经是 npm 的重要替代品，现代 Yarn 也支持 PnP、workspace 等能力。

这里容易产生一个疑问：既然一个 Node.js 版本通常会自带一个 `npm`，为什么 `pnpm`、`Yarn` 不也和 Node.js 版本绑定，而是还要额外管理包管理器版本？

原因是 `npm` 是 Node.js 官方发行版默认自带的包管理器，而 `pnpm`、`Yarn` 是第三方包管理器。它们有自己的发布节奏、配置格式、锁文件语义和依赖解析行为。如果一个项目使用 `pnpm@9`，另一个开发者本机全局安装的是 `pnpm@10`，就可能出现锁文件变化、安装行为差异、CI 和本地不一致等问题。

所以 Node.js 项目可以在 `package.json` 中写 `packageManager` 字段：

```json
{
  "packageManager": "pnpm@11.0.0"
}
```

它表示：这个项目希望使用指定版本的包管理器来安装依赖。也就是说，依赖版本由 `pnpm-lock.yaml` / `yarn.lock` / `package-lock.json` 固定，而包管理器自身的版本由 `packageManager` 字段固定。

`pnpm` 和 `Yarn` 不像 `npm` 那样天然随 Node.js 一起作为默认命令使用。常见方式有两种：

#### 方式1：Corepack

Corepack 是 Node.js 生态里用来管理包管理器版本的工具。它可以根据 `package.json` 里的 `packageManager` 字段，为项目准备指定版本的 `pnpm`、`Yarn` 或 `npm`。

可以把 Corepack 理解成“包管理器版本分发器/代理”：它解决的不是“安装哪些依赖”，而是“应该用哪个版本的包管理器来安装依赖”。

```bash
corepack enable
corepack use pnpm@latest
pnpm install
```

或者：

```bash
corepack enable
corepack use yarn@stable
yarn install
```

执行 `corepack use pnpm@latest` 或 `corepack use yarn@stable` 后，`package.json` 中会出现类似字段：

```json
{
  "packageManager": "pnpm@11.0.0"
}
```

{% note warning %}
Corepack 是 Node.js 发行版里附带的工具，但不是像 `npm` 那样的默认主包管理器。不同 Node.js 安装来源对 Corepack 的处理可能不同：有的会自带但默认不启用，有的系统包可能会拆开或不提供。遇到 `corepack: command not found` 时，可以再检查当前 Node.js 的安装来源。
{% endnote %}

#### 方式2：全局安装

也可以直接用 `npm` 全局安装：

```bash
npm install -g pnpm
npm install -g yarn
```

这种方式容易理解，但团队项目里更推荐使用 Corepack + `packageManager` 字段，因为它能固定每个项目应该使用的包管理器版本。

### npm / pnpm / Yarn 常用命令

三者的日常命令大体相似：

| 动作 | npm | pnpm | Yarn |
|------|-----|------|------|
| 安装全部依赖 | `npm install` | `pnpm install` | `yarn install` |
| 添加运行时依赖 | `npm install react` | `pnpm add react` | `yarn add react` |
| 添加开发依赖 | `npm install -D vite` | `pnpm add -D vite` | `yarn add -D vite` |
| 删除依赖 | `npm uninstall react` | `pnpm remove react` | `yarn remove react` |
| 运行脚本 | `npm run dev` | `pnpm dev` 或 `pnpm run dev` | `yarn dev` 或 `yarn run dev` |
| 严格按锁文件安装 | `npm ci` | `pnpm install --frozen-lockfile` | `yarn install --immutable` |

`pnpm` 的一个重要特点是全局 store：同一个包内容只在磁盘上保存一份，各项目的 `node_modules` 通过链接指向 store，因此大量项目共存时通常更省空间。

`Yarn` 现代版本有两种常见安装形态：一种是传统的 `node_modules`，另一种是 Plug'n'Play (PnP)。PnP 不再生成庞大的 `node_modules` 目录，而是通过 `.pnp.cjs` 等文件描述依赖解析关系。不过不少工具链对 `node_modules` 的兼容性更直观，所以是否启用 PnP 要看项目生态。

### dependencies 与 devDependencies

`dependencies` 通常表示运行时依赖，例如 Web 应用真正运行时需要的库。

`devDependencies` 表示开发期依赖，例如构建工具、测试工具、代码格式化工具：

以 `pnpm` 为例：

```bash
pnpm add react
pnpm add -D vite typescript eslint
```

### 锁文件

锁文件用于固定依赖树：

| 包管理器 | 锁文件 |
|----------|--------|
| npm | `package-lock.json` |
| pnpm | `pnpm-lock.yaml` |
| Yarn | `yarn.lock` |

团队项目中应该提交锁文件，这样 CI/CD 和其他开发者安装到的依赖版本才更一致。

安装依赖时：

```bash
npm install
pnpm install
yarn install
```

CI 环境中更推荐使用严格安装：

```bash
npm ci
pnpm install --frozen-lockfile
yarn install --immutable
```

## C# / .NET

C# 的现代生态基本围绕 .NET SDK、项目文件、解决方案文件和 NuGet 展开。

### .NET SDK 版本管理

.NET SDK 可以多个版本并存。安装后可以查看本机 SDK 和 Runtime：

```bash
dotnet --list-sdks
dotnet --list-runtimes
dotnet --version
```

一台电脑上有多个 SDK 时，`dotnet` CLI 会按照自己的规则选择一个 SDK。项目可以通过 `global.json` 固定“这个仓库使用哪个 SDK 来执行 dotnet 命令”：

```json
{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature"
  }
}
```

当目录中存在 `global.json` 时，`dotnet` CLI 会根据其中配置选择 SDK。它解决的是“用哪个 SDK 构建项目”的问题，而不是 NuGet 包版本的问题，也不是直接指定程序运行时一定使用哪个 Runtime。

项目真正面向的运行时版本通常写在 `.csproj` 里：

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
</PropertyGroup>
```

可以粗略理解成：

| 配置 | 作用 |
|------|------|
| `global.json` | 选择构建项目时使用的 .NET SDK |
| `.csproj` 里的 `TargetFramework` | 声明项目面向哪个 .NET 目标框架 |
| `PackageReference` | 声明 NuGet 包依赖 |

### Arch Linux 上的多版本 .NET

Arch Linux 上通常通过 `pacman` 安装 .NET 相关包：

```bash
sudo pacman -S dotnet-sdk
sudo pacman -S dotnet-runtime
sudo pacman -S aspnet-runtime
```

如果需要旧版本 SDK/Runtime，可以先搜索可用包名：

```bash
pacman -Ss dotnet-sdk
pacman -Ss dotnet-runtime
pacman -Ss aspnet-runtime
```

Arch 仓库里常见做法是用带版本后缀的包同时安装多个版本，例如 `dotnet-sdk-8.0`、`dotnet-runtime-8.0` 这一类包名。具体有哪些版本取决于当前仓库。

安装多个 SDK 后，推荐在每个仓库根目录放一个 `global.json`：

```bash
dotnet new globaljson --sdk-version 10.0.100
```

然后用下面的命令确认当前项目实际选到了哪个 SDK：

```bash
dotnet --version
dotnet --info
```

{% note info %}
如果只是开发应用，安装 SDK 通常就够了，因为 SDK 包含构建工具和对应 Runtime。只运行已发布的应用时才更常单独安装 Runtime；ASP.NET Core Web 应用还会涉及 `aspnet-runtime`。
{% endnote %}

### SDK 与 Runtime 的关系

.NET 里常见几个概念：

- SDK：开发工具包，包含 `dotnet` CLI、编译构建工具、模板，以及对应 Runtime。
- Runtime：只负责运行已经构建好的 .NET 应用。
- ASP.NET Core Runtime：运行 ASP.NET Core Web 应用需要的运行时组件。

所以“SDK 和 Runtime 是否绑定安装”要分场景：

- 从开发者角度：安装某个 .NET SDK 时，一般会同时得到对应 Runtime，因此可以直接 `dotnet build`、`dotnet run`。
- 从部署角度：服务器如果只负责运行程序，可以只安装 Runtime；如果是 Web 应用，通常安装 ASP.NET Core Runtime。
- 从多版本角度：不同大版本的 SDK 和 Runtime 可以 side-by-side 共存，通过 `global.json`、`TargetFramework` 和 runtime roll-forward 规则共同决定构建与运行行为。

### 解决方案与项目

C# / .NET 里经常会遇到两个层级：

- **项目**：通常对应一个 `.csproj` 文件，描述一个可构建单元，例如控制台程序、类库、Web API、测试项目。
- **解决方案**：通常对应 `.sln` 或 `.slnx` 文件，用来把多个项目组织在一起，方便统一打开、构建、测试和管理项目引用。

一个常见结构：

```text
DemoApp/
├── DemoApp.sln
├── src/
│   └── DemoApp.Api/
│       └── DemoApp.Api.csproj
└── tests/
    └── DemoApp.Tests/
        └── DemoApp.Tests.csproj
```

常用命令：

```bash
dotnet new sln -n DemoApp
dotnet new webapi -n DemoApp.Api -o src/DemoApp.Api
dotnet new xunit -n DemoApp.Tests -o tests/DemoApp.Tests
dotnet sln add src/DemoApp.Api/DemoApp.Api.csproj
dotnet sln add tests/DemoApp.Tests/DemoApp.Tests.csproj
dotnet add tests/DemoApp.Tests/DemoApp.Tests.csproj reference src/DemoApp.Api/DemoApp.Api.csproj
```

这里 `dotnet add ... reference ...` 添加的是**项目引用**，表示测试项目依赖业务项目；下面的 NuGet 包管理添加的是**包引用**，表示项目依赖外部包。

### NuGet 包管理

NuGet 是 .NET 的包管理系统；`dotnet add package`、`dotnet restore` 这些 `dotnet` 命令背后调用的就是 NuGet restore / package resolution 机制。

C# 的 NuGet 依赖通常写在 `.csproj` 文件里：

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>
</Project>
```

常用命令：

```bash
dotnet new console -n Demo
dotnet add package Newtonsoft.Json
dotnet add package Newtonsoft.Json --version 13.0.3
dotnet list package
dotnet remove package Newtonsoft.Json
dotnet restore
dotnet build
dotnet run
```

执行 `dotnet add package Newtonsoft.Json` 后，`.csproj` 里会新增 `PackageReference`；执行 `dotnet restore` 时，NuGet 会根据这些 `PackageReference` 下载并解析依赖。

### 中央包版本管理

当解决方案里有多个项目时，可以使用 `Directory.Packages.props` 集中管理 NuGet 包版本：

```xml
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>
</Project>
```

此时具体项目只声明包名：

```xml
<PackageReference Include="Newtonsoft.Json" />
```

### 锁文件

NuGet 支持生成 `packages.lock.json`，用于锁定 restore 得到的包版本：

```xml
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>
```

CI 中可以使用 locked mode：

```bash
dotnet restore --locked-mode
```

## Java

Java 生态一般分为两层：

- JDK 版本管理：决定用哪个 Java 编译器和运行时。
- 构建/依赖管理：Maven 或 Gradle 负责下载依赖、编译、测试、打包。

### JDK 版本管理

常见选择：

- SDKMAN!：在 Linux/macOS 上比较常见，可以安装和切换不同发行版的 JDK，也能管理 Maven、Gradle 等 JVM 生态工具。
- `archlinux-java`：Arch Linux 提供的系统级 Java 环境切换工具。
- jEnv：偏向本机多 JDK 切换。
- asdf：通用版本管理器。
- IDE 内置管理：IntelliJ IDEA、Eclipse、VS Code 都可以配置项目 JDK。

如果你在 Arch Linux 上，`archlinux-java` 本身就是很自然的选择：

```bash
archlinux-java status
archlinux-java get
sudo archlinux-java set java-21-openjdk
```

它管理的是系统安装在 `/usr/lib/jvm/` 下的 Java 环境，并切换系统默认的 `java`、`javac` 等命令。它的优点是和 Arch 包管理器集成很好；缺点是偏系统级，项目级切换和自动下载不同发行版 JDK 的体验不如 SDKMAN!。

使用 SDKMAN!：

```bash
sdk list java
sdk install java 21.0.4-tem
sdk use java 21.0.4-tem
sdk default java 21.0.4-tem
java -version
```

是否需要从 `archlinux-java` 换成 SDKMAN!，可以按场景判断：

| 场景 | 建议 |
|------|------|
| 只在 Arch 上开发，使用 Arch 官方 OpenJDK 包 | 继续用 `pacman + archlinux-java` 就很好 |
| 经常需要切换 Temurin、Zulu、GraalVM 等不同 JDK 发行版 | SDKMAN! 更方便 |
| 希望 Maven、Gradle、JDK 都由同一个工具安装和切换 | SDKMAN! 更方便 |
| 项目已经用 Gradle toolchain 指定 JDK | 本机只要能提供对应 JDK 即可，不一定必须换工具 |

{% note primary %}
Java 项目真正的可复现性通常不只靠本机默认 `java` 命令。Gradle 可以使用 toolchain 指定语言版本；Maven 可以通过 `maven.compiler.release` 指定编译目标。也就是说，本机版本管理工具负责“装好 JDK”，构建工具负责“项目实际用哪个 JDK/目标版本”。
{% endnote %}

### Maven

Maven 项目的核心文件是 `pom.xml`：

```xml
<project>
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>demo</artifactId>
  <version>0.1.0</version>

  <properties>
    <maven.compiler.release>21</maven.compiler.release>
  </properties>

  <dependencies>
    <dependency>
      <groupId>com.google.guava</groupId>
      <artifactId>guava</artifactId>
      <version>33.3.1-jre</version>
    </dependency>
  </dependencies>
</project>
```

常用命令：

```bash
mvn compile
mvn test
mvn package
```

Maven 使用本地仓库缓存依赖，默认路径通常是 `~/.m2/repository`。

### Gradle

Gradle 项目的核心文件可以是 Groovy DSL 的 `build.gradle`，也可以是 Kotlin DSL 的 `build.gradle.kts`：

```kotlin
plugins {
    application
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("com.google.guava:guava:33.3.1-jre")
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.0")
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
```

Gradle 常用命令：

```bash
./gradlew build
./gradlew test
./gradlew run
```

{% note info %}
团队项目中通常推荐使用 Gradle Wrapper，也就是提交 `gradlew`、`gradlew.bat` 和 `gradle/wrapper/`。这样大家使用的是项目指定的 Gradle 版本，而不是各自机器上随便安装的版本。
{% endnote %}

### Java 依赖锁定

Java 生态的锁文件不像 Rust、Node.js 那么统一：

- Gradle 支持 dependency locking，可以生成 `gradle.lockfile`。
- Maven 默认更依赖显式版本号、父 POM、BOM、镜像仓库和构建规范来保证稳定性。

Maven 中常见的版本集中管理方式是 `dependencyManagement`：

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.junit</groupId>
      <artifactId>junit-bom</artifactId>
      <version>5.11.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

## Rust

Rust 的工具链体验比较统一：`rustup` 管版本，`cargo` 管项目、依赖、构建、测试和发布。

### Rust 版本管理

安装 Rust 后，通常会得到 `rustup`：

```bash
rustup show
rustup update
rustup default stable
rustup toolchain install nightly
rustup override set nightly
```

Rust 有几个常见发布通道：

- `stable`：稳定版，日常项目首选。
- `beta`：测试即将发布的版本。
- `nightly`：每日构建版，包含一些实验性功能。

项目中可以使用 `rust-toolchain.toml` 固定工具链：

```toml
[toolchain]
channel = "stable"
components = ["rustfmt", "clippy"]
```

### Cargo 包管理

Rust 项目的核心文件是 `Cargo.toml`：

```toml
[package]
name = "demo"
version = "0.1.0"
edition = "2024"

[dependencies]
serde = { version = "1.0", features = ["derive"] }
```

常用命令：

```bash
cargo new demo
cargo add serde --features derive
cargo build
cargo run
cargo test
cargo fmt
cargo clippy
```

### Cargo.lock

`Cargo.lock` 会记录完整依赖树的精确版本。

一般规则：

- 可执行程序项目：提交 `Cargo.lock`。
- 库项目：现在也常见提交 `Cargo.lock`，尤其是项目中包含示例、测试或工作区时；但发布到 crates.io 的库真正约束外部使用者的仍然是 `Cargo.toml` 中的版本范围。

Rust 生态里依赖来源也比较灵活：

```toml
[dependencies]
regex = "1"
my_lib = { path = "../my_lib" }
some_crate = { git = "https://github.com/example/some_crate.git", rev = "abcdef" }
```

## C/C++

C/C++ 的包管理最复杂，因为它横跨：

- 编译器：GCC、Clang、MSVC。
- 标准库：libstdc++、libc++、MSVC STL。
- 构建系统：Make、CMake、Meson、Bazel 等。
- 系统依赖：Linux 发行版包、Homebrew、MSYS2、vcpkg、Conan 等。
- 平台 ABI：不同平台和编译器之间二进制兼容性并不总是简单。

### 为什么有时只要 include 就行

初学 C/C++ 时很容易产生一种感觉：很多库好像不需要像 Python 那样 `pip install`，直接 `#include` 就能用。这里要拆开看：

- `#include <stdio.h>`、`#include <vector>` 这类来自 C 标准库或 C++ 标准库的头文件，通常随编译器/系统开发包一起安装，所以看起来像“自带”。
- `#include <unistd.h>`、`#include <sys/socket.h>` 这类常见于 Unix/Linux 的系统头文件，通常来自系统 C 库和系统开发环境。
- 很多第三方 C/C++ 库不是自带的，只是你的系统、IDE、课程环境、Docker 镜像或开发包已经提前装好了。
- `#include` 只解决“编译器能看到声明”的问题，不等于已经把库的实现链接进程序。

例如使用 `math.h` 里的函数时，可能需要额外链接数学库：

```c
#include <math.h>
#include <stdio.h>

int main() {
    printf("%f\n", sqrt(2.0));
    return 0;
}
```

在某些 Linux 环境中需要：

```bash
gcc main.c -lm
```

再比如使用 OpenSSL：

```c
#include <openssl/ssl.h>
```

这行 include 能否成功，取决于系统里有没有安装 OpenSSL 的开发文件，例如头文件和库文件。Linux 上常见包名可能是：

```bash
sudo apt install libssl-dev
sudo pacman -S openssl
```

编译时还可能需要告诉编译器头文件和库的位置：

```bash
gcc main.c -I/path/to/include -L/path/to/lib -lssl -lcrypto
```

所以 C/C++ 的依赖可以分成两层：

| 层次 | 解决什么问题 | 常见参数/工具 |
|------|--------------|---------------|
| 头文件 include path | 编译时能不能找到声明 | `-I`、`target_include_directories` |
| 库文件 link path / link library | 链接时能不能找到实现 | `-L`、`-l`、`target_link_libraries` |

C/C++ 包管理器做的事情，本质上就是帮你下载/编译这些头文件和库文件，并把 include path、link path、编译选项等信息交给构建系统。

### 编译器版本管理

Linux 上常见方式：

```bash
gcc --version
g++ --version
clang --version
```

可以通过系统包管理器安装不同版本：

```bash
sudo apt install gcc-13 g++-13 clang-18
```

也可以用 `update-alternatives` 配置默认版本，或者在项目构建命令中显式指定：

```bash
CC=gcc-13 CXX=g++-13 cmake -S . -B build
```

Windows 上常见选择：

- Visual Studio / MSVC
- LLVM/Clang
- MinGW-w64 / MSYS2

macOS 上常见选择：

- Apple Clang
- Homebrew 安装的 LLVM/GCC

### CMake

CMake 是 C/C++ 项目最常见的跨平台构建配置工具之一。典型的 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.28)
project(demo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(demo main.cpp)
```

构建命令：

```bash
cmake -S . -B build
cmake --build build
```

CMake 本身不是包管理器，但它常常作为集成入口，与 Conan、vcpkg、系统包一起使用。

### vcpkg

vcpkg 是微软主导的 C/C++ 包管理器，适合跨平台安装 C/C++ 库。现代项目常用 manifest 模式，在项目中写 `vcpkg.json`：

```json
{
  "dependencies": [
    "fmt",
    "spdlog"
  ]
}
```

配合 CMake：

```bash
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build
```

vcpkg 通常通过固定 vcpkg 仓库版本、`builtin-baseline` 和自定义 registry 来提高依赖可复现性。

### Conan

Conan 是另一个常见 C/C++ 包管理器。典型 `conanfile.txt`：

```ini
[requires]
fmt/11.0.2

[generators]
CMakeDeps
CMakeToolchain
```

安装依赖：

```bash
conan install . --output-folder=build --build=missing
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
cmake --build build
```

Conan 支持 profile，用于描述编译器、标准库、构建类型、目标平台等信息：

```bash
conan profile detect
conan profile show
```

也支持 lockfile：

```bash
conan lock create conanfile.txt --lockfile-out=conan.lock
```

### 系统包管理器

很多 C/C++ 依赖也可以直接使用系统包管理器：

```bash
sudo apt install libssl-dev zlib1g-dev
brew install openssl zlib
pacman -S mingw-w64-x86_64-openssl
```

这种方式简单，但跨平台可复现性相对弱一些，因为不同系统仓库里的版本、编译选项和安装路径可能不同。

### C/C++ 小结

C/C++ 项目想要稳定复现，通常要同时固定：

- 编译器版本
- C/C++ 标准版本，例如 C++17、C++20、C++23
- 构建系统版本，例如 CMake 版本
- 第三方库版本
- 编译选项和目标平台
- ABI 相关设置，例如 MSVC runtime、libstdc++ ABI 等

这也是 C/C++ 包管理比 Python、Node.js、Rust 更复杂的主要原因。

## 常见文件是否应该提交

| 文件 | 是否提交 | 说明 |
|------|----------|------|
| `.python-version` | 通常提交 | 让项目固定 Python 版本 |
| `.venv/` | 不提交 | 虚拟环境是本机产物 |
| `requirements.txt` | 通常提交 | pip 项目依赖入口 |
| `pyproject.toml` | 提交 | Python 项目元数据与依赖声明 |
| `uv.lock` / `poetry.lock` / `pdm.lock` | 应用项目提交 | 用于固定依赖树 |
| `.node-version` | 通常提交 | 固定 Node.js 版本，`fnm` 支持 |
| `.nvmrc` | 通常提交 | 固定 Node.js 版本 |
| `package.json` | 提交 | Node.js 项目元数据与依赖声明 |
| `package.json` 中的 `packageManager` | 通常提交 | 固定 pnpm/Yarn/npm 的包管理器版本 |
| `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` | 通常提交 | 固定 Node.js 依赖树 |
| `global.json` | 通常提交 | 固定 .NET SDK 版本 |
| `.csproj` | 提交 | C# 项目文件 |
| `.sln` / `.slnx` | 通常提交 | C# 解决方案文件，组织多个项目 |
| `packages.lock.json` | 推荐提交 | 固定 NuGet restore 结果 |
| `pom.xml` | 提交 | Maven 项目文件 |
| `build.gradle(.kts)` | 提交 | Gradle 项目文件 |
| `gradle/wrapper/`、`gradlew` | 推荐提交 | 固定 Gradle 版本 |
| `Cargo.toml` | 提交 | Rust 项目文件 |
| `Cargo.lock` | 应用项目提交 | 固定 Rust 依赖树 |
| `CMakeLists.txt` | 提交 | C/C++ 构建配置 |
| `vcpkg.json` | 提交 | vcpkg manifest |
| `conanfile.txt` / `conanfile.py` | 提交 | Conan 依赖声明 |
| `build/` | 不提交 | 构建产物 |

## 一个粗略选择建议

如果只是希望快速进入某门语言的主流开发方式，可以从下面的组合开始：

| 语言 | 推荐起步组合 |
|------|--------------|
| Python | `uv + pyproject.toml + uv.lock` |
| Node.js | `fnm + Corepack + pnpm`，简单项目直接 `npm` 也可以 |
| C# / .NET | `pacman/dotnet-install + global.json + dotnet CLI + NuGet` |
| Java | Arch 上可用 `pacman + archlinux-java + Gradle Wrapper/Maven`；跨发行版多 JDK 可考虑 SDKMAN! |
| Rust | `rustup + Cargo` |
| C/C++ | `CMake + vcpkg` 或 `CMake + Conan`，小项目也可以先用系统包管理器 |

## 总结

版本控制和包管理的目标其实很朴素：**让项目在不同时间、不同机器、不同开发者手上尽量得到同样的构建结果**。

几种语言里，Rust 的 `rustup + cargo` 一体化程度最高；Node.js 工具很多但模式清晰；Python 现在可以优先从 `uv` 这条主线理解；C# 和 Java 更依赖成熟的构建系统；C/C++ 因为历史包袱、平台差异和 ABI 问题，包管理和构建复现通常最复杂。

实际项目里可以重点关注三个问题：

1. 项目使用哪个语言/运行时/编译器版本？
2. 直接依赖和间接依赖是否被清楚记录？
3. CI 和其他开发者能否根据仓库里的文件复现同样的环境？

只要这三个问题回答清楚，版本控制和包管理就已经走在比较可靠的路线上了。
